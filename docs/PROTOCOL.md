# 协议参考 / Protocol Reference

本文件记录两层的接口细节：**USB 层（CH340/CH341 芯片）** 与 **链路层（STC-ISP 时序）**。

> ### 关于本文件的严谨性说明
>
> 下列内容按证据强度分三类标注：
>
> - ✅ **已实测**：来自本项目的源码、真机日志，或可用
>   [`tools/verify_divisor.py`](../tools/verify_divisor.py) 复算。
> - 📖 **来自公开驱动/文档**：来自 Linux `ch341.c`、WCH 厂商驱动、stcgal 文档，
>   本项目按其实现，但**未逐字节用 USB 抓包独立验证**。
> - ❓ **未验证/不确定**：明确标注，不要当作事实引用。
>
> 如果你能用 USB 抓包（如 `usbmon` / Wireshark）补上证据，非常欢迎提 PR。

## 1. USB 设备层

### 1.1 识别

| 项目 | 值 | 来源 |
|---|---|---|
| VID:PID | `0x1A86:0x7523` | 📖 WCH 官方；✅ 本项目按其查找并成功命中 |
| 接口 | 接口 0，类 `0xFF`（厂商自定义） | 📖 |
| 端点 | `0x02` Bulk OUT、`0x82` Bulk IN、`0x81` 中断 IN | 📖（本项目只用前两个） |
| 最大包长 | Bulk 32 字节、中断 8 字节 | 📖；✅ 发送按 32 字节分块已实测可用 |
| 芯片版本 | 实测 `0x31` | ✅ 通过 `0x5F` 请求读出 |

> 芯片版本 `0x31` 是**实测值**，用于决定写寄存器的分支行为（见 1.3）。

### 1.2 控制传输

请求类型：`0x40` = 主机→设备（OUT），`0xC0` = 设备→主机（IN）。📖

| 宏 | 值 | 方向 | 用途 | 状态 |
|---|---|---|---|---|
| `CH341_REQ_READ_VERSION` | `0x5F` | IN | 读芯片版本（读 2 字节，取第 1 字节） | ✅ 实测 |
| `CH341_REQ_SERIAL_INIT` | `0xA1` | OUT | 串口初始化 | ✅ 实测 |
| `CH341_REQ_WRITE_REG` | `0x9A` | OUT | 写寄存器 | ✅ 实测 |
| `CH341_REQ_MODEM_CTRL` | `0xA4` | OUT | modem 控制线（DTR/RTS） | 📖 已实现，Android pty 下难以独立验证 |
| `CH341_REQ_READ_REG` | `0x95` | IN | 读寄存器 | ❓ **本项目未使用**，仅列出 |

`0xA4` 的载荷是**取反**后的 modem 位掩码：`(~mcr) & 0xFFFF`，
其中 `BIT_DTR = 1 << 5`、`BIT_RTS = 1 << 6`。📖

### 1.3 寄存器

写寄存器的 `wValue` 是"寄存器地址对"拼接：**低字节 = 第一个寄存器，高字节 = 第二个寄存器**。
因此设波特率时 `wValue = (0x13 << 8) | 0x12`，`wIndex` = 分频编码值。✅ 实测

| 寄存器 | 地址 | 含义 | 状态 |
|---|---|---|---|
| 预分频 | `0x12` | prescaler | 📖 |
| 分频 | `0x13` | divisor | 📖 |
| 线路控制 | `0x18` | LCR，本项目为 `0x80 \| 0x40 \| 0x03`（使能收发 + 8 数据位） | 📖 |
| 线路控制 2 | `0x25` | LCR2 | 📖 |
| 流控 | `0x27` | 定义但本项目未使用 | ❓ |

**版本相关的分支**（✅ 实测于 `0x31`）：

```
version > 0x27  ->  分频值 OR 上 0x80
version >= 0x30 ->  额外写一次 (0x25 << 8) | 0x18，载荷为 LCR
```

## 2. 波特率分频算法

### 2.1 公式

```
baud = 48000000 / (2^(12 - 3*ps - fact) * div)

约束：0 <= ps <= 3     0 <= fact <= 1     2 <= div <= 256
编码（写入 wIndex）：((0x100 - div) << 8) | (fact << 2) | ps
```

时钟 `CH341_CLKRATE = 48 MHz`。📖 算法本身与 Linux `ch341.c` 的
`ch341_calc_divisor()` 同源，本项目以 Python 重写（见
[THIRD_PARTY.md](THIRD_PARTY.md)），**未复制代码**。

### 2.2 已在源码中实现的两点

1. **就近取整**：比较向上/向下取整的相对误差决定 `div` 是否 `+1`。
2. **偶分频降半**：若 `fact == 1` 且 `div` 为偶数，则 `div //= 2` 且 `fact = 0`
   （等价速率，但避免某些实现下的抖动）。📖

### 2.3 数值自检表

由 [`tools/verify_divisor.py`](../tools/verify_divisor.py) 生成。
"是否全局最优"是把全部 `(ps, fact, div)` 组合穷举后比较得出的结论 ——
也就是说，**2400 这个档位不是"能用"，而是数学上的最优解**。

| 目标 baud | 输出编码 | ps / fact / div | 实际 baud | 误差 | 全局最优？ |
|---|---|---|---|---|---|
| 1200 | `0xB201` | 1 / 0 / 78 | 1201.9 | 0.1603% | ✅ |
| **2400** | **`0xD901`** | **1 / 0 / 39** | **2403.8** | **0.1603%** | ✅ |
| 9600 | `0xB202` | 2 / 0 / 78 | 9615.4 | 0.1603% | ✅ |
| 19200 | `0xD902` | 2 / 0 / 39 | 19230.8 | 0.1603% | ✅ |
| 38400 | `0x6403` | 3 / 0 / 156 | 38461.5 | 0.1603% | ✅ |
| 57600 | `0x8003` | 3 / 0 / 128 | 46875.0 | 18.62% | ❌ 被 `MAX_BPS` 截断 |
| 115200 | `0x8003` | 3 / 0 / 128 | 46875.0 | 59.31% | ❌ 被 `MAX_BPS` 截断 |

UART 的异步容错一般允许约 2–3% 的总误差，因此 0.16% 有充足余量 ——
这解释了为什么固定 2400 一直很稳。

### 2.4 已知缺陷：`MAX_BPS` 截断

```python
MIN_BPS = (48000000 + (1 << 12) * 256 - 1) // ((1 << 12) * 256)   # = 46
MAX_BPS = 48000000 // ((1 << 9) * 2)                              # = 46875
```

`MIN_BPS`/`MAX_BPS` 的写法沿用内核驱动，导致**任何高于 46875 的请求都被静默钳位**。
WCH 驱动配置 115200 用的是 `ps=3, fact=0, div=52`（编码 `0xCC83`，实际 115384 baud），
**说明算法能表达 115200，是这个上限把它挡住了**。

⚠️ 早期文档曾声称"115200 对应分频字节 `0xCC83`" —— 那是 WCH 驱动的值，
**不是本项目代码的输出**。详见 [DEBUG_LOG.md #14](DEBUG_LOG.md)。

## 3. 链路层：STC-ISP 时序

> ⚠️ 本节描述的是**观察到的行为**，不是对 STC-ISP 协议的独立逆向。
> 协议实现完全由 `stcgal` 负责，本项目不解析、不构造任何 STC 协议包。
> 如需协议细节，请查阅 stcgal 源码与其 `doc/reverse-engineering/` 目录。

### 3.1 关键前提：STC89 只在上电时进 ISP

- 复位（按 RST 键）**不会**进入 bootloader；必须**冷启动**（断电 → 上电）。
- 因此烧录时需要在 `stcgal` 等待期间给单片机上电。✅ 实测
- 这也是全流程唯一无法自动化的环节（除非额外做 DTR 控制供电的硬件）。

### 3.2 观察到的流程

```
stcgal                          ch340_bridge.py                STC89C52
  │                                    │                          │
  │ 打开 /dev/pts/N (pyserial)          │                          │
  │ 设 termios 波特率 2400 ─────────────►│ 3 ms 内轮询到               │
  │                                    │ 写 0x12/0x13 = 0xD901     │
  │ 发送握手包 ─────────────────────────►│ Bulk OUT 0x02 ──────────►│ 等待上电
  │                                    │                          │ ← 人为冷启动
  │ ◄───────────────────────────────────│ ◄────── Bulk IN 0x82 ─────│ 返回芯片信息
  │ 打印 Target model / F002 / 8KB / 11.030MHz / BSL 6.6C          │
  │ 切换到 2400 baud（本项目与握手同值）  │                          │
  │ 擦除 → 写入 → 设置选项 ─────────────►│ ────────────────────────►│
  │ Disconnected!                       │                          │
```

### 3.3 实测到的芯片信息（STC89C52RC/LE52RC）

| 项目 | 值 |
|---|---|
| Magic | `F002` |
| Code flash | 8.0 KB |
| EEPROM | 6.0 KB |
| 工作频率 | 11.030 MHz |
| BSL 版本 | 6.6C |
| 选项 | `cpu_6t=False, bsl_pindetect=False, eeprom_erase=False, clock_gain=high, ale=True, xram=True, watchdog_por=False` |

这些值来自一次成功烧录的日志，**不随本项目代码变化**，可作为"链路是否正常"的判据：
只要能打印出上面的信息，说明 USB、pty、波特率三段都通了。

### 3.4 为什么把传输速率压到 2400

见 [README · 设计决策 2](../README.md#2-为什么传输波特率锁死-2400)，两条并列原因：
pty 波特率同步延迟；以及 `MAX_BPS` 截断。原始归因无法从已有日志中区分。
